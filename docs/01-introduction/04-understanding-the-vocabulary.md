# Understanding the Vocabulary

## 1. PostgreSQL 的对象层级

在 PostgreSQL 中，可以把数据组织结构理解为：**Instance（实例）→ Database（数据库）→ Schema（模式）→ Table（表）**。

| 层级     | 含义                                 | 作用                         |
| -------- | ------------------------------------ | ---------------------------- |
| Instance | 正在运行的 PostgreSQL 服务环境       | 管理其中的数据库             |
| Database | 实例中的一个数据库                   | 连接时需要选择具体数据库     |
| Schema   | 数据库内部的命名空间，可理解为文件夹 | 对表等对象进行分组和隔离命名 |
| Table    | schema 中的表                        | 存储实际的数据               |

连接 PostgreSQL 时，连接信息通常同时指定**服务器地址**和**数据库名称**。例如 Supabase 项目通常提供一个名为 `postgres` 的数据库；数据库名称也可以按项目需要设置。

本课把 instance、server、cluster 用来描述运行中的 PostgreSQL 服务环境。理解层级时，先抓住“一个运行中的服务环境可以包含多个数据库”即可。

---

## 2. Schema：数据库内部的命名空间

连接到某个数据库后，数据库中的表并不是直接放在数据库根目录下，而是属于某个 schema。

Schema 主要**用于组织对象**，并允许不同 schema 中存在同名对象，例如：

- `app.users`：应用业务数据
- `admin.users`：管理用途的数据
- `reporting.users`：报表用途的数据

PostgreSQL 默认提供 `public` schema。若创建表时没有指定 schema，通常会根据当前会话的 `search_path` 决定创建位置。在课程演示环境中，新建的 `users` 表进入了 `public`。

对于一般应用，先使用 `public` 通常就足够了，不必为了分层而过早创建很多 schema。

Schema 也可以用于多租户隔离，或让扩展把自己的对象放在独立 schema 中，避免和应用对象混在一起。具体是否采用这些设计，要根据团队的权限管理、部署和维护需求决定。

**注意：`schema` 这个词有两种常见含义。**

1. 在 PostgreSQL 对象层级中，schema 是数据库内部的命名空间，例如 `public`。
2. 在“表结构（table schema）”的语境中，schema 指表的定义，包括列、数据类型和约束等。

因此，“这个表属于哪个 schema？”问的是它位于哪个命名空间；“把这个表的 schema 给我看看”通常是在问表结构。

## 3. `search_path`：未限定名称时去哪里找对象

`search_path` 是 PostgreSQL 的会话配置，**规定在 SQL 没有写出 schema 前缀时，按什么顺序查找对象**。

```sql
SHOW search_path;
```

课程演示环境返回的路径类似：

```sql
"$user", public, extensions
```

其中：

- `"$user"` 是特殊占位项，表示与当前数据库用户同名的 schema（如果存在）。
- `public` 是接下来查找的 schema。
- `extensions` 是之后查找的 schema；这是课程演示环境中的配置，不代表所有 PostgreSQL 环境都一定包含它。

例如执行：

```sql
SELECT * FROM users;
```

PostgreSQL 会依照 `search_path` 的顺序查找名为 `users` 的表。课程环境中，用户同名的 schema 不存在，于是继续在 `public` 中找到 `users`。

也可以明确指定 schema，避免依赖搜索顺序：

```sql
SELECT * FROM public.users;
```

如果指定的 schema 中没有该表，例如：

```sql
SELECT * FROM extensions.users;
```

PostgreSQL 就会报告关系（relation）不存在。这里的 relation 是 PostgreSQL 对表等关系型对象使用的术语；在这个例子里，错误表示 `extensions` schema 中没有 `users` 这张表。

**创建表时还有一个容易混淆的细节：**

- 未指定 schema 的 `CREATE TABLE` 会把表创建到 `search_path` 中第一个存在的 schema，而不是像查询那样逐个寻找一个已经存在的同名表；
- 如果当前用户没有在该 schema 中创建对象的权限，创建操作会失败。
- 因此，课程环境中 `CREATE TABLE users (...)` 最终创建在 `public`，是因为 `$user` 对应的 schema 不存在，`public` 成为可用的目标 schema。

## 4. 查看表属于哪个 Schema

课程中创建了一张简单的 `users` 表：

```sql
CREATE TABLE users (
    id INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    name TEXT NOT NULL
);
```

这里 `id` 使用 identity 自动生成整数值，并作为主键。

`name` 是不允许为 `NULL` 的文本列。创建语句没有写 schema 前缀，因此创建位置由 `search_path` 决定。

可以通过 `information_schema.tables` 查看当前数据库中的普通表及其所属 schema：

```sql
SELECT table_schema, table_name
FROM information_schema.tables
WHERE table_schema = 'public'
  AND table_type = 'BASE TABLE';
```

`table_schema` 表示表所属的 schema，`table_name` 表示表名；`BASE TABLE` 用于筛选普通基表，而不是视图等其他类型的对象。

---

## 本节要点

- PostgreSQL 的对象层级是 **实例 → 数据库 → schema → 表**。
- 连接时选择实例中的一个数据库；schema 则用于组织该数据库内部的表和其他对象。
- `public` 是默认提供的 schema，许多应用使用它就足够了。
- `search_path` 决定未写 schema 前缀时对象的查找顺序；课程演示环境包含 $user、`public` 和 `extensions`，实际配置可能不同。
- 查询未限定的表名时，PostgreSQL 按 `search_path` 顺序查找；创建未限定的表时，则使用搜索路径中第一个可用的 schema。
- 遇到 `relation does not exist`，除了检查表名和数据库是否正确，也要检查 schema 和 `search_path` 是否符合预期。
